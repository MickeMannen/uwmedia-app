# Instructions for AI coding agents

These rules apply to any coding agent working in this repo.

## Files and data
- Never write or delete files outside this repo folder. That includes the
  Python app's repo (on the owner's machine
  `~/development/uwmedia`, a read-only reference), the user's
  media folders and the app's real data folders (macOS:
  `~/Library/Application Support/org.christersson.uwmedia/`). For test
  files use the repo's fixtures or a temporary folder.
- Every writable path in the app comes from `lib/core/app_paths.dart`
  (`userConfigDir()`, `userDataDir()`, `userCacheDir()`, `appTempDir()`).
  Never build one elsewhere or hard-code one.
- `docs/spec.md` is the spec. Field names, units and defaults in §4 and
  the renderer rules in §5 are not up for reinterpretation; a deliberate
  difference from the Python app is one listed in §10, or a new entry
  added there first.
- `docs/README.md` lists the documents and says where a new one goes.

## Git
- Never commit unless the owner asks for that specific commit. Exception
  (owner, 2026-11-12): on `v0.1`, a commit per round of work after
  the default suite passes, pushed to `gitea`.
- Never add dive-log files (FIT, UDDF, SSRF, XML or CSV exports) to git.
  They contain device serial numbers and personal IDs.
- Never add photos or videos to git without the owner's review of each
  file and its metadata.
- Two remotes, kept apart: `gitea` (the owner's server) and `github`
  (the public repo). A push or a release goes to the remote the owner
  names, never to both by default.
- `v0.1` is where the work and its whole history live. (It took the
  place of `development`, a name too general: owner, 2026-11-22.) It is on
  Gitea only and never goes to GitHub (owner, 2026-11-21), nor does any
  other development branch.
- `main` holds releases only, with a history of its own, the same on
  both remotes: it starts as one commit of the tree of the first release,
  and each release after it is one more commit whose tree is
  `v0.1`'s at that release (`git read-tree -u --reset
  v0.1` on `main`, then the commit; the `/release` skill does
  this). `main` and `v0.1` share no history, so nothing is ever
  merged between them.
- The temporary branch `move_github` (branched from `main`, on GitHub)
  is where the GitHub workflows (builds, signing) are made to work
  without a string of fix-up releases on `main`. When they work, its
  changes are squashed into one commit on `main`, the same changes are
  applied to `v0.1` as a commit of their own (a patch, not a
  merge), and the branch is deleted.
- The GitHub hold of 2026-10-17 was lifted on 2026-11-21 (owner); a
  push to GitHub still needs the owner's word each time.

## Tests
Follow `CONTRIBUTING.md`:
- Run the default suite (`tool/run_tests.sh 1`: format check, analyzer,
  tests) before saying work is done, and `tool/run_tests.sh 4` and the
  speed check (`tool/perf_check.sh`) before a release. Never lower a
  speed baseline or record a slower one without the owner's word.
- Always pass `tool/run_tests.sh` a choice (1-5) when there is no
  terminal.
- Report failures as they are. Don't skip or weaken tests to make them
  pass, and don't regenerate golden images to make a diff go away.
- A module brought over from the Python app gets its tests from the
  Python test cases and a fixture generated by the Python code
  (`/fixtures`), not from its own output.

## Roadmap
- `docs/roadmap_v0.1.0.md` is the one list of work still to do for the
  coming release (v0.1.0), tests included. Tick items off there as they
  land; at the end of the round a finished item moves to
  `docs/roadmap_v0.1.0_done.md`, under the same section and with its
  number. Sections are lettered and items numbered ("C12"); a number is
  never reused, and a new item takes the next free number of its section.
- `docs/roadmap_v0.2.0.md` holds what comes after the release and is not
  worked from until the owner says so.

## Changelog
User-facing changes get a bullet under `## [Unreleased]` in `CHANGELOG.md`.
Follow the existing style there.
